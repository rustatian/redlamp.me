Нужна наименьшая скорость k, при которой Koko успевает за h часов. Для горки 7 и k = 3 Koko ест 3, 3 и 1 банан: это 3 часа. Остаток в 1 банан занимает целый час, потому что за один час Koko ест из одной горки. Горка из p бананов занимает ⌈p / k⌉ часов, где ⌈x⌉ - это x, округлённое вверх: ⌈7 / 3⌉ = 3. Сумму часов по всем горкам назовём часы(k). Число горок - n.

Brute Force пробует k = 1, 2, 3, ... и для каждого k считает часы(k). Для piles = [3, 6, 7, 11] и h = 8 выходит часы(1) = 27, часы(2) = 15, часы(3) = 10 и часы(4) = 8. Первое k, при котором часов не больше 8, - это 4. Brute Force делает не больше M проверок по n делений, где M = max(piles): это O(n · M) в худшем случае. Худший вход: n = 104 горок по 109 бананов и h = 104. Тогда ответ 109, и Brute Force делает 109 проверок по 104 делений. Это 1013 делений: слишком долго.

Решение 1. Binary Search по ответу

Возьмём piles = [3, 6, 7, 11] и посчитаем часы для двух скоростей. При k = 3 выходит 1 + 2 + 3 + 4 = 10 часов. При k = 4 выходит 1 + 2 + 2 + 3 = 8 часов.

При большей скорости часов не больше. Горка 7 занимает 3 часа при k = 3 и 2 часа при k = 4. Для любой горки p число p / (k + 1) меньше p / k, поэтому ⌈p / (k + 1)⌉ не больше ⌈p / k⌉. Каждое слагаемое не растёт, и сумма часы(k) тоже не растёт. Вот часы(k) для k от 1 до 11 и ответ на вопрос «часы(k) ≤ 8?»:

Часы при каждой скорости k, piles = [3, 6, 7, 11]
k1234567891011
часы(k)27151088655554
часы(k) ≤ 8нетнетнетдададададададада

Ответы идут как «нет, нет, нет, да, да, ...»: если k подходит, то подходит и k + 1. Наименьшее подходящее k - первое «да». Binary Search ищет первое «да» среди k = 1, ..., 11 и не хранит Array: часы(k) считаются в момент проверки.

Границы поиска. Значение lo = 1: при k = 0 Koko ничего не ест. Значение hi = max(piles) = 11: при k = 11 каждая горка занимает 1 час, всего n = 4 часа, а по условию h ≥ n. Поэтому hi подходит всегда, и ответ лежит в [lo, hi]. При h = n, как в примере 2 (n = 5, h = 5), ответ равен max(piles) = 30. При k = 29 горка 30 занимает 2 часа, а остальные 4 горки занимают по 1 часу: всего 6 часов, а это больше h = 5. При любом k меньше max(piles) самая большая горка занимает не меньше 2 часов, и всего часов не меньше n + 1.

Шаг поиска: mid = (lo + hi) // 2, потом часы(mid). Для h = 8 поиск идёт так. При lo = 1 и hi = 11 берём mid = 6: часы(6) = 1 + 1 + 2 + 2 = 6 ≤ 8. Скорость 6 подходит, поэтому ответ не больше 6: hi = 6. Дальше mid = 3 и часы(3) = 10 > 8. Скорости 1 и 2 дают ещё больше часов, поэтому ответ больше 3: lo = 4. Дальше mid = 5 и часы(5) = 8 ≤ 8: hi = 5. Дальше mid = 4 и часы(4) = 8 ≤ 8: hi = 4. Теперь lo = hi = 4, остался один кандидат. Ответ 4 после 4 проверок.

Правило. Инвариант: ответ лежит в [lo, hi]. Если часы(mid) ≤ h, то mid подходит и ответ не больше mid: hi = mid. Иначе ответ больше mid: lo = mid + 1. Цикл идёт, пока lo < hi. В конце lo = hi, и это ответ.

Ход hi = mid оставляет mid в отрезке, потому что сама скорость mid может быть ответом. В примере при lo = 4 и hi = 5 середина mid = 4 подходит, и hi = 4 сохраняет ответ 4. Цикл заканчивается: при lo < hi середина меньше hi, поэтому hi = mid уменьшает hi, а lo = mid + 1 увеличивает lo.

В отрезке [1, 11] 11 кандидатов. После каждой проверки остаётся не больше половины кандидатов, с округлением вверх: 6, 3, 2, 1. Это 4 проверки. Для max(piles) = 109 проверок не больше 30: 229 = 536 870 912 < 109 ≤ 230 = 1 073 741 824.

Пример 3: piles = [30, 11, 23, 4, 20] и h = 6. Скорость 22 даёт 2 + 1 + 2 + 1 + 1 = 7 часов, а это больше 6. Скорость 23 даёт 2 + 1 + 1 + 1 + 1 = 6 часов. Первое «да» - 23, это ответ.

В коде проверяемая скорость называется mid, а ⌈p / mid⌉ записано как (p + mid - 1) // mid. Для p = 7 и mid = 3 это 9 // 3 = 3, для p = 6 и mid = 3 это 8 // 3 = 2. Добавка mid − 1 превращает неполный час в целый, а // отбрасывает остаток.

class Solution:
    def minEatingSpeed(self, piles: list[int], h: int) -> int:
        lo, hi = 1, max(piles)
        while lo < hi:
            mid = (lo + hi) // 2
            hours = sum((p + mid - 1) // mid for p in piles)
            if hours <= h:
                hi = mid  # mid подходит: ответ не больше mid
            else:
                lo = mid + 1  # при скорости mid часов больше h: при меньшей скорости их тоже больше
        return lo

Время: O(n log M) в худшем случае, где M = max(piles): не больше ⌈log2 M⌉ проверок по n делений. При n = 104 и M = 109 это не больше 30 · 104 = 3 · 105 делений. Дополнительная память: O(1) в худшем случае: числа lo, hi, mid и hours. Функция sum складывает слагаемые по одному и не строит list. Вход piles и ответ не считаем.

Типичные ошибки

  • p // mid вместо (p + mid - 1) // mid. Для piles = [3, 6, 7, 11], h = 8 и mid = 3 выходит 1 + 2 + 2 + 3 = 8 часов вместо 10. Условие 8 ≤ 8 выполнено. При mid = 2 выходит 1 + 3 + 3 + 5 = 12 часов > 8, поэтому поиск возвращает 3 вместо 4: неполные часы не посчитаны.
  • hi = mid - 1 после «да». Для piles = [7] и h = 2 при lo = 1, hi = 7 середина mid = 4 даёт 2 часа ≤ 2. Ход hi = 3 теряет ответ 4. Дальше mid = 2 даёт 4 часа > 2, lo = 3, и цикл возвращает 3, хотя часы(3) = 3 > 2.
  • lo = mid вместо lo = mid + 1. Для piles = [7] и h = 2 после mid = 4 выходит hi = 4. Дальше mid = 2 даёт lo = 2, потом mid = 3 даёт lo = 3. При lo = 3 и hi = 4 середина снова равна 3, часы(3) = 3 > 2, и lo остаётся 3. Цикл не заканчивается.
  • Проверка hours == h вместо hours <= h. Для piles = [3, 6, 7, 11] и h = 9 ни одно k не даёт ровно 9 часов: часы(3) = 10 и часы(4) = 8. Проверка всегда отвечает «нет», и поиск возвращает 11 вместо 4.
  • Ответ ⌈sum(piles) / h⌉. Для piles = [1, 1, 1, 1, 10] и h = 5 формула даёт ⌈14 / 5⌉ = 3, но часы(3) = 1 + 1 + 1 + 1 + 4 = 8 > 5. Koko не делит час между горками. Ответ 10: часы(10) = 5 и часы(9) = 6.
  • lo = 0 вместо lo = 1. Для piles = [1] и h = 1 при lo = 0 и hi = 1 середина mid = 0, и (p + mid - 1) // mid делит на 0: ZeroDivisionError. Примеры условия проходят: их ответы 4, 30 и 23 больше 1, и mid не доходит до 0.

Оба вида вопросов спрашивают сумму чисел с номерами от l до r. Разница только в списке: вопрос вида 1 берёт стоимости в порядке входа, вопрос вида 2 берёт их в порядке неубывания.

Два списка

В первом примере v = [6, 4, 2, 7, 2, 7]. Те же стоимости в порядке неубывания: u = [2, 2, 4, 6, 7, 7]. Вопрос 2 3 6 спрашивает u3 + u4 + u5 + u6 = 4 + 6 + 7 + 7 = 24. Вопрос 1 3 4 спрашивает v3 + v4 = 2 + 7 = 9. Вопрос 1 1 6 спрашивает сумму всех шести чисел v: 6 + 4 + 2 + 7 + 2 + 7 = 28.

Вопросы не меняют стоимости, поэтому список u один для всех вопросов. Sorting нужен один раз, до первого вопроса.

Решение 1. Prefix Sum для v и для u

Посчитаем суммы начал списка v из примера: первое число 6, первые два 6 + 4 = 10, первые три 10 + 2 = 12 и так далее. Запишем эти суммы в список pv и поставим 0 в начало: pv = [0, 6, 10, 12, 19, 21, 28]. Теперь pv[i] это сумма первых i чисел v. Каждое следующее число pv стоит одно сложение: pv[i] = pv[i − 1] + vi. Такой же цикл по списку u даёт pu = [0, 2, 4, 8, 14, 21, 28].

Вопрос 1 3 4: pv[4] = 19 это сумма первых четырёх чисел v, а pv[2] = 10 это сумма первых двух. Разность 19 − 10 = 9 убирает первые два числа, и остаётся v3 + v4 = 9.

Правило. Сумма чисел с номерами от l до r равна p[r] − p[l − 1]: из суммы первых r чисел уходят первые l − 1. Вопрос вида 1 берёт p = pv, вопрос вида 2 берёт p = pu.

Вопрос 2 3 6: pu[6] − pu[2] = 28 − 4 = 24. Вопрос 1 1 6: pv[6] − pv[0] = 28 − 0 = 28. Число p[0] = 0 нужно для вопроса с l = 1: та же формула работает без отдельного if.

Номера камней в условии идут с 1, а список Python начинается с 0: v1 лежит в v[0]. Формулу это не меняет: номер i в pv и pu означает «первые i чисел», и вопрос читает p[r] и p[l − 1] без сдвига. В коде t это число type из условия.

import sys

input = sys.stdin.readline
n = int(input())
v = list(map(int, input().split()))
# u это стоимости по неубыванию; sorted() создаёт новый список и не меняет v
u = sorted(v)

# pv[i] это сумма первых i чисел v, pu[i] это сумма первых i чисел u
pv = [0]
for x in v:
    pv.append(pv[-1] + x)
pu = [0]
for x in u:
    pu.append(pu[-1] + x)

m = int(input())
out = []
for _ in range(m):
    t, l, r = map(int, input().split())
    p = pv if t == 1 else pu
    # числа с номерами от l до r: первые r чисел без первых l - 1
    out.append(p[r] - p[l - 1])
print("\n".join(map(str, out)))

Время: O(n log n + m) в худшем случае. Sorting делает O(n log n) сравнений один раз. Два цикла делают 2n сложений, в примере 12, а каждый вопрос стоит одно вычитание. При n = m = 105 это 2 · 105 сложений и 105 вычитаний. Дополнительная память: O(n) для любого входа: списки v, u, pv и pu хранят вместе 4n + 2 числа. Ответ отдельно: в out m чисел.

Наибольший ответ: 105 камней по 109 дают 105 · 109 = 1014. Целые числа Python не переполняются. В C++ 32-битный тип int хранит числа до 2 147 483 647. Это меньше 1014, поэтому там для суммы нужен 64-битный тип.

Что не подходит

Brute Force складывает числа от l до r заново для каждого вопроса. Если начинать с суммы 0, вопрос стоит r − l + 1 сложений. Три вопроса примера стоят 4 + 2 + 6 = 12 сложений. При n = m = 105 и вопросах по всем камням это 105 · 105 = 1010 сложений: слишком долго. Пересчёт сумм стоит O(n · m) в худшем случае.

Вызов sorted(v) внутри цикла вопросов каждый раз строит один и тот же список u из n чисел. При n = 105 и 105 вопросах вида 2 это 105 · 105 = 1010 записанных чисел, не считая сравнений: слишком долго. Каждый вызов делает O(n log n) сравнений, поэтому m таких вызовов стоят O(m · n log n) в худшем случае.

Типичные ошибки

  • Строки v.sort() и u = v вместо u = sorted(v) упорядочивают сам список v, а u это тот же список, не копия. Тогда pv считает суммы упорядоченного списка, и вопрос 1 3 4 получает 4 + 6 = 10 вместо 9.
  • u = v.sort() даёт u = None: sort() меняет v и возвращает None. Цикл for x in u останавливает программу с ошибкой TypeError.
  • Формула p[r] − p[l] теряет число с номером l. Вопрос 1 3 4: pv[4] − pv[3] = 19 − 12 = 7 вместо 9, пропало v3 = 2.

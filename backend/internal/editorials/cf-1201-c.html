Нужно найти наибольшую медиану, которую можно получить за k операций «прибавить 1».

Сколько операций нужно для медианы m

Пример: a = [1, 2, 1, 1, 1] и k = 5. После Sorting a = [1, 1, 1, 1, 2]. Номера идут с нуля, поэтому медиана стоит на месте a[n // 2] = a[2] и равна 1.

Чтобы медиана стала не меньше 3, в итоговом Array должны быть минимум 3 числа не меньше 3: медиана - третье число по порядку из 5. Дешевле всего поднять 3 самых больших числа 1, 1 и 2. Они требуют 2 + 2 + 1 = 5 операций. Три самых маленьких числа 1, 1 и 1 требуют 2 + 2 + 2 = 6 операций: числу 2 до 3 не хватает 1, а не 2.

Верхняя часть - это числа с места n // 2 до конца: a[n // 2:] = [1, 1, 2]. В ней (n + 1) / 2 самых больших чисел. Цена медианы m - сумма max(0, m − v) по всем v из верхней части. Назовём её cost(m). Для m = 3 это (3 − 1) + (3 − 1) + (3 − 2) = 5, для m = 4 это 3 + 3 + 2 = 8. Число v ≥ m ничего не стоит: для v = 2 и m = 1 разность 1 − 2 равна −1, а max(0, −1) = 0. После подъёма до 3 получится Array [1, 1, 3, 3, 3] с медианой 3.

Цена не убывает с ростом m: каждое слагаемое при m + 1 не меньше, чем при m. Поэтому проверка cost(m) ≤ k монотонная. При k = 5 она даёт «да» для m = 1, 2, 3 (цена 0, 2 и 5) и «нет» для m = 4 (цена 8 > 5). Ответ - последнее «да», то есть 3.

Brute Force проверяет m = 1, 2, 3, ... подряд, пока цена не больше k. Большой вход: n = 199 999, медиана равна 1, а 99 999 чисел правее равны 109, при k = 109. Ответ равен 109. Это 109 + 1 проверка, и в каждой складывается 100 000 чисел: около 1014 сложений. Это слишком долго.

Решение 1. Binary Search

В примере ответ лежит между lo = a[2] = 1 и hi = a[2] + k = 1 + 5 = 6. Медиана 1 получается без операций: cost(1) = 0. Медиана 7 невозможна: она требует от a[2] = 1 шести операций при k = 5. В общем виде границы такие: lo = a[n // 2] и hi = a[n // 2] + k. Медиана lo = a[n // 2] получается без операций. Медиана a[n // 2] + k + 1 невозможна, потому что её цена не меньше k + 1: слагаемое для v = a[n // 2] уже равно k + 1.

Каждый шаг проверяет середину mid = (lo + hi + 1) // 2. Сначала lo = 1, hi = 6, mid = 4 и cost(4) = 8 > 5. Каждая медиана от 4 и выше стоит не меньше 8, поэтому hi = 3. Дальше mid = (1 + 3 + 1) // 2 = 2 и cost(2) = 2 ≤ 5: медиана 2 подходит, и lo = 2. Затем mid = (2 + 3 + 1) // 2 = 3 и cost(3) = 5 ≤ 5, поэтому lo = 3. Теперь lo = hi = 3: ответ 3 после 3 проверок.

Плюс 1 в mid нужен для наибольшего ответа. При lo = 2 и hi = 3 середина (2 + 3) // 2 равна 2, то есть lo. Если медиана 2 подходит, то lo = mid ничего не меняет, и цикл не кончается. С + 1 середина равна 3, и отрезок сужается на каждом шаге.

Цену cost(mid) можно посчитать без цикла Python по числам. Пример: half = [1, 1, 2] и mid = 2. Числа меньше 2 - это 1 и 1, их количество p = 2. Каждое стоит 2 − 1 = 1, а число 2 равно mid и ничего не стоит. Значит, cost(2) = 2 · 2 − (1 + 1) = 2: это mid · p − (сумма первых p чисел). Для mid = 4 все три числа меньше 4, поэтому p = 3 и cost(4) = 4 · 3 − (1 + 1 + 2) = 8.

В списке half числа идут по возрастанию, поэтому числа меньше mid всегда стоят в его начале. Число p возвращает bisect_left(half, mid): это Binary Search по отсортированному списку. Сумма первых p чисел в коде - это sum(half[:p]). При n = 199 999 цикл с max(0, mid − v) по верхней части сделал бы до 30 · 100 000 = 3 · 106 шагов Python за все проверки. По оценке из уроков Python делает около 107 простых шагов в секунду, поэтому такой цикл тоже успевает: это около 0,3 с. Срез и sum - встроенные операции, цикла Python по числам в них нет, и Решение 1 работает быстрее этого цикла.

import sys
from bisect import bisect_left

data = sys.stdin.buffer.read().split()
n, k = int(data[0]), int(data[1])
a = sorted(map(int, data[2:2 + n]))
half = a[n // 2:]  # медиана и все числа правее
# медиана half[0] получается без операций, ответ не больше half[0] + k
lo, hi = half[0], half[0] + k
while lo < hi:
    mid = (lo + hi + 1) // 2
    p = bisect_left(half, mid)  # p чисел меньше mid, остальные стоят 0
    cost = mid * p - sum(half[:p])
    if cost <= k:
        lo = mid
    else:
        hi = mid - 1
print(lo)

Время: O(n log n + n log k) в худшем случае. Sorting стоит O(n log n). В отрезке от a[n // 2] до a[n // 2] + k ровно k + 1 ≤ 109 + 1 значений. Каждая проверка оставляет из N значений не больше (N + 1) // 2: в примере 6, 3, 2 и 1. Поэтому отрезок сужается до одного значения не больше чем за 30 проверок: 230 = 1 073 741 824 > 109 + 1. Каждая проверка ищет p через bisect_left за O(log n) и складывает срез из p ≤ (n + 1) / 2 чисел. При n = 199 999 все срезы вместе - не больше 3 · 106 чисел. Дополнительная память: O(n) в худшем случае: отсортированный список a хранит n чисел, список half хранит (n + 1) / 2 чисел, а срез half[:p] хранит ещё до (n + 1) / 2 чисел. Кроме среза, поиск хранит только lo, hi, mid, p и cost. Вход (список data) и ответ считаем отдельно.

Решение 2. Greedy

После Sorting верхняя часть примера - [1, 1, 2]. Группа - это первые c чисел верхней части, уже поднятые до уровня level. Сначала в группе одно число a[2] = 1: level = 1 и c = 1. Медиана равна level.

Следующее число a[3] = 1 стоит 1 · (1 − 1) = 0 операций и входит в группу: c = 2. Чтобы группа достигла следующего числа a[i], нужно c · (a[i] − level) операций. Если столько операций есть, число присоединяется к группе. Для level = 1 и c = 2 следующее число a[4] = 2 больше level, поэтому подъём медианы на 1 стоит c = 2 операции: каждое число группы растёт на 1. Число a[4] = 2 стоит 2 · (2 − 1) = 2 ≤ 5 операций, поэтому k = 5 − 2 = 3, level = 2 и c = 3. Числа кончились, и группа - вся верхняя часть. Затраты группы 0 + 2 = 2 равны cost(2) из Решения 1: Greedy считает ту же цену по частям.

Остаток k операций делится между c числами группы. Каждый подъём на 1 стоит c операций, и хватает на k // c подъёмов. Ответ level + k // c = 2 + 3 // 3 = 3.

Пример: a = [1, 2, 3, 4, 5] и k = 2, верхняя часть [3, 4, 5]. Число 4 стоит 1 · (4 − 3) = 1 операцию, поэтому k = 1, level = 4 и c = 2. Число 5 стоит 2 · (5 − 4) = 2 операции, а осталась 1: цикл останавливается. Группе хватает 1 // 2 = 0 подъёмов, и ответ равен 4 + 0 = 4. Ответ 4 меньше 5, поэтому число 5 поднимать не нужно. Так всегда: если группа не может достичь следующего числа, остаток k меньше c · (a[i] − level), поэтому level + k // c меньше a[i].

import sys

data = sys.stdin.buffer.read().split()
n, k = int(data[0]), int(data[1])
a = sorted(map(int, data[2:2 + n]))
med = n // 2
# первые c чисел из a[med:] подняты до уровня level
level, c = a[med], 1
for i in range(med + 1, n):
    need = c * (a[i] - level)
    if need > k:
        break
    k -= need
    level = a[i]
    c += 1
print(level + k // c)

Время: O(n log n) в худшем случае: Sorting стоит O(n log n), а цикл делает не больше (n − 1) / 2 шагов. При n = 199 999 это не больше 99 999 шагов. Дополнительная память: O(n) в худшем случае: отсортированный список a хранит n чисел, а остальные переменные - только числа. Вход (список data) и ответ считаем отдельно.

Типичные ошибки

  • Нет Sorting. Для a = [5, 1, 1] и k = 1 оба решения выводят 1 вместо 2: без Sorting верхняя часть a[1:] = [1, 1], и подъём до 2 стоит 1 + 1 = 2 > 1. После Sorting верхняя часть [1, 5], cost(2) = 1 ≤ 1 и cost(3) = 2 > 1.
  • Число p = len(half): в сумму идут и числа, которые не меньше mid. Для a = [1, 1, 1, 1, 9] и k = 4 верхняя часть [1, 1, 9]. Число 9 даёт отрицательное слагаемое 5 − 9 = −4, поэтому при m = 5 сумма 4 + 4 − 4 = 4 ≤ 4, и решение выводит 5 вместо 3. С bisect_left получается p = 2 и cost(5) = 5 · 2 − (1 + 1) = 8 > 4.
  • Граница hi = max(a) вместо a[n // 2] + k. Для a = [1] и k = 109 поиск идёт по отрезку от 1 до 1 и выводит 1 вместо 1 000 000 001.
  • Сумма по всем n числам, а не по верхней части. Для a = [1, 2, 1, 1, 1] и k = 5 цена m = 3 равна 2 + 2 + 2 + 2 + 1 = 9 > 5, и решение выводит 2 вместо 3.

Нужна наименьшая ёмкость c, при которой все грузы уезжают не больше чем за days дней. Дни для данной c считает Greedy-погрузка: грузим по порядку, пока следующий груз помещается, а когда не помещается, начинаем новый день. Для weights = [3, 2, 2, 4, 1, 4] и c = 5 выходят дни [3, 2], [2], [4, 1], [4]: 4 дня. Для c = 6 выходят дни [3, 2], [2, 4], [1, 4]: 3 дня.

Brute Force пробует c = max(weights), max(weights) + 1, ... и останавливается на первой c, которая укладывается в days дней. Меньше max(weights) брать нельзя: самый тяжёлый груз не поместится. Для weights = [3, 2, 2, 4, 1, 4] и days = 3 это три погрузки: c = 4 даёт 5 дней, c = 5 даёт 4 дня, c = 6 даёт 3 дня. Ответ 6. Каждая погрузка проходит все n грузов. Всего O(n · S) шагов в худшем случае, где S = sum(weights). Худший вход: n = 5 · 104 грузов по 500 и days = 1. Тогда ответ равен сумме 2,5 · 107, и Brute Force делает около 2,5 · 107 погрузок по 5 · 104 шагов. Это около 1,25 · 1012 шагов: слишком долго.

Решение 1. Binary Search по ёмкости

Сначала проверим, что Greedy-погрузка даёт наименьшее число дней при данной ёмкости. Возьмём c = 14 и грузы 1, 2, ..., 10 из примера 1: вес груза равен его номеру. Greedy грузит [1, 2, 3, 4] и не берёт груз 5: 10 + 5 = 15 > 14. Любой другой план перевозит в первый день не больше 4 грузов. Возьмём план [1, 2, 3]. Его второй день - грузы 4 и 5. У Greedy груз 4 уже уехал, а груз 5 помещается: 5 ≤ 14. Поэтому Greedy везёт груз 5 во второй день и берёт ещё груз 6: 5 + 6 = 11 ≤ 14. После двух дней у Greedy уехали 6 грузов, у плана 5.

То же верно для каждого дня. Пусть у Greedy уехали первые g грузов, у другого плана первые p, и p ≤ g. В следующий день другой план берёт грузы с номера p + 1 по q. Greedy начинает с номера g + 1 ≥ p + 1, поэтому грузы с g + 1 по q составляют часть грузов плана и помещаются. Для g = 4, p = 3 и q = 5 это только груз 5. Значит, после дня у Greedy уехало не меньше грузов, чем у плана. Если какой-то план укладывается в days дней, то Greedy тоже.

Назовём дни(c) число дней Greedy-погрузки при ёмкости c. Вот дни(c) для c от 4 до 9 и ответ на вопрос «дни(c) ≤ 3?»:

Если c подходит, то подходит и c + 1: план для c остаётся правильным при большей ёмкости. Поэтому ответы идут как «нет, нет, да, да, ...», и наименьшая подходящая c - первое «да». Binary Search ищет первое «да» и не хранит Array значений c.

Границы поиска. Значение lo = max(weights) = 4: при меньшей c груз 4 не помещается ни в один день. Значение hi = sum(weights) = 3 + 2 + 2 + 4 + 1 + 4 = 16: все грузы едут в один день, а по условию days ≥ 1. Поэтому hi подходит всегда, и ответ лежит в [lo, hi].

Шаг поиска: mid = (lo + hi) // 2, потом Greedy-погрузка при c = mid. Для days = 3 поиск идёт от lo = 4 и hi = 16 и делает 4 проверки: середины 10, 7, 5, 6 дают 2, 3, 4 и 3 дня. Если дни(mid) ≤ 3, то ответ не больше mid: hi = mid. При mid = 5 выходит 4 дня > 3, а при меньшей ёмкости дней не меньше: lo = 6. Ответ 6.

Правило. Инвариант: ответ лежит в [lo, hi]. Если Greedy-погрузка при c = mid укладывается в days дней, то mid подходит и ответ не больше mid: hi = mid. Иначе ответ больше mid: lo = mid + 1. Цикл идёт, пока lo < hi. В конце lo = hi, и это ответ.

Отрезок [4, 16] содержит 13 значений. После проверки остаётся не больше половины длины, округлённой вверх: длины 13, 7, 4, 2, 1. Это 4 проверки: 13 ≤ 24 = 16. Отрезок [lo, hi] не длиннее S = sum(weights), а S ≤ 5 · 104 · 500 = 2,5 · 107. Проверок не больше 25: 224 = 16 777 216 < 2,5 · 107 ≤ 225 = 33 554 432.

class Solution:
    def shipWithinDays(self, weights: list[int], days: int) -> int:
        lo, hi = max(weights), sum(weights)
        while lo < hi:
            mid = (lo + hi) // 2
            used, load = 1, 0
            for w in weights:
                if load + w > mid:  # груз не помещается: начинаем новый день
                    used += 1
                    load = 0
                load += w
            if used <= days:
                hi = mid  # mid подходит: ответ не больше mid
            else:
                lo = mid + 1  # при ёмкости mid дней больше days: при меньшей их тоже больше
        return lo

Время: O(n log S) в худшем случае, где S = sum(weights) ≤ 2,5 · 107: не больше 25 проверок по n шагов. При n = 5 · 104 это не больше 1,25 · 106 шагов. Дополнительная память: O(1) в худшем случае: числа lo, hi, mid, used, load и w. Функции max и sum проходят weights по одному числу и не строят list. Вход weights и ответ не считаем.

Типичные ошибки

  • lo = 1 вместо max(weights). Для weights = [10, 1, 1] и days = 3 ответ 10. При c = 2 код кладёт груз 10 в новый день, хотя он не помещается: used = 2, load = 10. Груз 1 открывает ещё один день, used = 3, и последний груз 1 помещается: 1 + 1 = 2 ≤ 2. Три дня ≤ 3, ёмкость 2 «подходит», и поиск возвращает 2 вместо 10.
  • load + w >= mid вместо load + w > mid. Груз может заполнить день ровно до c. Для weights = [3, 3, 3] и days = 3 ответ 3: каждый груз едет в свой день. При c = 3 условие 0 + 3 >= 3 открывает новый день ещё до первого груза, а 3 + 3 >= 3 открывает ещё два. Выходит used = 4 > 3, и поиск возвращает 4 вместо 3.
  • hi = sum(weights) // days. Для weights = [7, 2, 5, 10, 8] и days = 2 это 32 // 2 = 16. Ёмкость 16 даёт дни [7, 2, 5], [10], [8]: 3 дня > 2. Ответ 18: [7, 2, 5], [10, 8]. Каждый из days дней везёт не больше c, поэтому days · c ≥ sum(weights): здесь 2 · c ≥ 32, то есть c ≥ 16. Значение sum(weights) // days - нижняя граница ответа, а не верхняя, и поиск на [10, 16] возвращает 16 вместо 18.
